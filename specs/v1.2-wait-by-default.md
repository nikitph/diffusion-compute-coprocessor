# v1.2 · Task: wait by default

Oct 29, 2026 · @CREDIT IQ

## Objective

Test whether pausing a sequence until its tool result arrives, then continuing with protected native editing, fixes the two failures v1.1 left open, without losing the mid-block property.

**Why.** v1.1 showed that results are used when they land (A7: 114/120 direct, 1.8% regressions), and that 239 of 240 A4 results landed inside a block still being denoised. Its failures all came from *not* waiting:

- Late results went unused unless dependent text was erased (hidden-delay 0/6 at 10–40 steps without re-masking), and erasing costs regressions (A4: 6.0%).
- Async multi-call Linux tasks scored 3/20 against 6/20 conventional, most likely because dependent calls fired before their inputs arrived.
- One stale completion broke the zero-stale target.

**Claim under test.** The novelty is *where* results land (mid-canvas, mid-block, revised around by editing), not *when* the model works (concurrency). If waiting keeps the first and fixes the failures, waiting becomes the default and async becomes a later optimisation for slow calls.

Model and setup are unchanged from v1.1: frozen LLaDA2.2-mini at the same revision, BF16, batch size 1, no fine-tuning, same tasks and seeds.

## Wait semantics

When a call is dispatched, the requesting sequence stops denoising until the result is locked; then it resumes with protected native editing (A7 rules) and no re-masking.

1. **Dispatch.** A call becomes eligible exactly as in v1.1 (complete call span, operand confidence ≥ τ = 0.9; for supplied-operand arithmetic, at the slot's scheduled step). Record the step index *t* and wall-clock time.
2. **Pause.** Run no forward passes, unmasking or edits for that sequence until the call completes. Canvas, masks and schedule position are held exactly as they were at *t*.
3. **Lock.** Insert the result into its native tool slot (v1.1 placement), mark it protected, and record wall-clock wait time.
4. **Resume.** Continue from step *t* with the remaining schedule unchanged. Protected native editing is on; `DELETE`/`SPLIT`/`MASK` remain suppressed on protected positions.
5. **Multiple calls.** Each call pauses the sequence independently. Up to 4 rounds per task, as in v1.1 F4. A call whose arguments are written after an earlier result has landed naturally sees that result.

**Delays under waiting.** v1.1 delays were measured in forward steps. Under waiting no steps pass during the pause, so a delay is applied as wall-clock time equal to *d* × the mean step time measured in v1.1, for *d* = 0, 10, 20, 40. The canvas state at lock time should therefore match delay 0; the cost appears only as wall-clock time. Report both.

**Not in scope.** Batch-level parking of paused sequences (batch size stays 1), speculative calls, and re-masking. The hybrid async rule is an optional extra condition only (L4 below).

## Conditions and task sets

Three task sets, each run with the wait condition plus the v1.1 conditions it must be compared against. Re-run the v1.1 comparison conditions in the same session rather than reusing old numbers, so drift between runs cannot explain a difference.

**Linux (27 tasks: the 7 prior + 20 multi-call)**

| ID | Condition |
| --- | --- |
| L0 | No tools |
| L1 | Conventional: call, then restart answer generation |
| L2 | Async, 4 rounds (v1.1) |
| L3 | **Wait**, 4 rounds, protected editing |
| L4 | Optional: wait only if the call's arguments are not yet fully committed or depend on an earlier pending result; otherwise async |

**Delayed-result controls (6 hidden-file + 6 arithmetic tasks, d = 0 / 10 / 20 / 40)**

| ID | Condition |
| --- | --- |
| D1 | Async, re-mask off (v1.1) |
| D2 | Async, re-mask on (v1.1) |
| D3 | **Wait**, protected editing, no re-mask |

**Arithmetic (the v1.1 240 tasks; block length 32, and 64 for the mid-block check)**

| ID | Condition |
| --- | --- |
| M4 | Matched prefill baseline (v1.1) |
| A7 | Reserved slot + protected editing, no wait (v1.1) |
| A7W | **Wait** + reserved slot + protected editing |

In the supplied-operand setup results are near-instant, so A7W should match A7. This is a non-inferiority check that waiting costs nothing where calls are fast, plus the first measurement of A7-style editing at block length 64.

## Hypotheses and gates (pre-registered)

These are fixed before any v1.2 run. Do not change prompts, tools, schedules or thresholds after the first run starts; any change means a new version.

| ID | Hypothesis | Gate |
| --- | --- | --- |
| H1 | Waiting fixes dependent multi-call tasks | L3 multi-call success ≥ L1 in the same session, and > L2 |
| H2 | Waiting does not hurt simple tool tasks | L3 on the 7 prior tasks ≥ L1 |
| H3 | Waiting removes the need for re-masking | D3 ≥ 6/6 hidden-file and ≥ 5/6 arithmetic at every delay |
| H4 | Waiting costs nothing when calls are fast | A7W direct within 2 answers of A7; regressions vs M4 ≤ 2% |
| H5 | Waiting keeps the mid-block property | A7W at block 64: ≥ 30% of results land in a block still masked, and direct ≥ A4's v1.1 block-64 score (109/120) |
| H6 | Waiting is safe by construction | 0 lock violations, 0 stray effects, 0 stale completions, 0 residual masks |

**How to read the outcome**

- H1–H6 all pass: waiting becomes the default. Async is kept only as an optimisation for slow calls, to be justified separately.
- H3 and H5 pass but H1 fails: late results are solved, but multi-call tasks fail for another reason (likely call quality). Classify every L3 failure by cause before drawing conclusions.
- H5 fails: waiting changes where results land. Report the arrival distribution; the mid-block claim then rests on v1.1's A4 alone.

Linux has only 20 multi-call tasks, so report exact paired counts and per-task outcomes, not significance tests. Arithmetic comparisons use exact two-sided McNemar tests on the paired 120 direct answers.

## Prerequisites, constraints, metrics, deliverables

**Before the first run**

- [ ] Fix the residual-mask bug (25 incomplete outputs in v1.1) and confirm 0 residual masks on the 36 smoke prompts.
- [ ] Implement the pause in the sampler and unit-test it: canvas, masks and step index identical before and after a pause with no result inserted.
- [ ] Re-confirm the v1.1 arithmetic and Linux contracts are unchanged (calc operations supported, tool schemas, 256-token result budget).
- [ ] Reproduce 5 A7 records from v1.1 exactly before starting.

**Constraints**

- Frozen weights; same model revision, seeds, block lengths, templates and few-shot examples as v1.1.
- Linux calls in fresh, network-disabled containers against the synthetic workspace only.
- No new prompting, tools or recovery turns after the first run begins.

**Metrics per record**

- Success (task-specific), strict text, calls made, rounds used.
- Per call: dispatch step, wait time (wall-clock), lock step, whether the result's block still had masks at lock.
- Total wall-clock time, split into denoising time and wait time.
- Safety counters: lock violations, stray effects, stale completions, residual masks.

**Deliverables**

1. A results summary in the v1.1 format: tables per task set, gate outcomes H1–H6, and per-task Linux outcomes with failure causes.
2. Raw records, call/commit event logs and timings in `results-v1.2/`, plus the exact source used.
3. A one-paragraph conclusion: is waiting the default, and what remains for async?

## Run order and budget

Run the cheapest, most diagnostic sets first, so a broken pause is caught before the 240-prompt runs.

1. Prerequisites above.
2. Delayed-result controls (D1–D3): 12 tasks × 4 delays × 3 conditions = 144 runs. Checks H3 and H6 quickly.
3. Linux, L0–L3 (and L4 if time allows): 27 tasks × 4–5 conditions. Checks H1, H2.
4. Arithmetic at block length 32: M4, A7, A7W on 240 tasks. Checks H4.
5. Arithmetic at block length 64: A7W on 240 tasks. Checks H5.

**Budget** (estimate, from v1.1 timings): about 2–4 GPU hours of sampling on one A100 80 GB, plus Linux container time. Most of the cost is the two 240-prompt arithmetic runs; if time is short, run step 5 before step 4, since H5 is the stronger result.
