# v1.1 · Next pilot: making results land and get used

Oct 28, 2026 · @CREDIT IQ

## Summary

v1.1 tests whether four engineering fixes raise how often results land, without losing how well they are used, on frozen LLaDA2.2-mini.

The two pilots so far split the problem in two. On LLaDA-8B, results landed but were ignored. On tool-trained LLaDA2.2-mini, results that landed were used: 4 of 6 direct insertions turned a wrong answer right, with no regressions. But insertions fired on only 7 of 36 arithmetic prompts. The gain is now limited by **firing**, not **use**.

**Hypothesis.** Placing results where the model was trained to read them, reserving slots before the model fills them, and re-opening dependent text when a result arrives will raise the firing rate to most eligible prompts, while use stays high and regressions stay near zero. No fine-tuning.

## Results so far

Both pilots used the same 36 synthetic arithmetic prompts (18 direct, 18 downstream); the mini pilot also ran 7 Linux tool tasks.

|  | LLaDA-8B (frozen) | LLaDA2.2-mini (frozen, tool-trained) |
| --- | --- | --- |
| Direct answers: base → insertion | 12/18 → 13/18 (best case) | 7/18 → 11/18 |
| Downstream decisions: base → insertion | 17/18 → 16–17/18 | 14/18 → 14/18 |
| Post-hoc correction, direct | 18/18 | 16/18 |
| Insertions fired | 54 across conditions | 7 of 36 prompts, all at the first step |
| Operand precision, lock violations | 100%, 0 | 100%, 0 |
| Locked value used in final answer | often not (e.g. `90364` locked, `90434` answered) | 4 of 6 direct insertions fixed a wrong answer; 0 regressions |
| Linux tools, answer present (6 read/compute) | — | 2/6 conventional, 2/6 async, 0/6 no tools |
| Committed write | — | performed only after commit, file exact |

Three findings carry into v1.1:

- **Representation matters.** Re-sending results as ordinary native tool messages fixed a wrong file copy under both samplers, so the custom reserved slot caused at least one failure.
- **Late results go unused.** A result held 40 steps arrived at answer step 37; its lock held but the answer never revisited it. The 32-round hold had expired.
- **Mostly between blocks.** All arithmetic insertions fired at the first step, after the equation's block was done. True mid-block injection is still largely untested.

## The four fixes

Each fix targets one observed failure and can be switched on or off independently, so its effect is measurable alone.

**F1 · Native result placement** (fixes: reserved-slot representation)

- Results arrive as the model's native tool-response turn, rendered by its own chat template, not as a custom protected span.
- For arithmetic, declare a `calc(expression)` tool so the model calls it natively. The kernel answers the call; the response is inserted as a native tool message.
- Keep the custom-slot path as an ablation (F1 off).

**F2 · Higher firing** (fixes: absent and occupied opportunities)

Two variants, tested separately:

- **F2a · Reserved slot.** The prompt template ends every equation as ` <a> <op> <b> =  ` followed by a pre-masked, protected slot of fixed width. The sampler never lets the model write into it; only the kernel can. Triggers on the completed operand span, before `=` is written.
- **F2b · Variable reference.** The model writes `Answer: <ref r1>` instead of a number; the runtime fills every reference when `r1` lands. The model only has to point at the result, never copy it.

**F3 · Re-mask on arrival** (fixes: late results going unused)

- Replace the bounded hold with an event rule: when a result lands, re-mask the unlocked tokens of every span that depends on it and was committed after the call was submitted, then let denoising continue.
- Dependent span, v1.1 definition: the rest of the current block plus any later block already started. Locked results and the prompt are never re-masked.
- Budget: at most one re-mask per result, and at most 2 per sequence, to bound cost and avoid oscillation.

**F4 · Multi-turn runner** (fixes: one-call scaffold)

- Allow up to 4 call/result rounds per task, each with the same async rules (reads from drafts, writes after commit).
- Raise the result budget from 64 to 256 tokens; longer outputs are truncated with a marker and stay readable through a follow-up `read_file` with an offset.
- Count multi-call tasks separately so one-call results stay comparable with the last pilot.

## Conditions, tasks, controls

The arithmetic set grows to 240 prompts so a real effect can reach significance; everything else keeps the last pilot's setup (frozen LLaDA2.2-mini, same revision, BF16, A100 80 GB, batch size 1, lock-protected sampler).

**Task sets**

| Set | Composition | Size |
| --- | --- | --- |
| Arithmetic | 5 digit sizes (5, 8, 10, 12, 15) · 3 operations (+, −, ×) · 2 task types (direct, downstream) · 8 seeded operand pairs | 240 |
| Arithmetic, original | the 36 prompts from both earlier pilots, for continuity | 36 |
| Linux tools, one call | the 7 tasks from the last pilot | 7 |
| Linux tools, multi-call | new: CSV and log tasks that need 2–4 reads or a read then `run` | 20 |

Downstream thresholds are set within ±1% of the true value, so the base model cannot pass by rough estimation. This removes the near-ceiling problem of the earlier pilots.

**Arithmetic conditions**

| ID | Condition | Fixes on |
| --- | --- | --- |
| A0 | Base, no tools | — |
| A1 | Last pilot's insertion (custom slot, bounded hold) | — |
| A2 | Native `calc` tool, conventional (call, then restart answer) | F1 |
| A3 | Native `calc` tool, mid-denoising | F1 + F3 |
| A4 | Reserved slot | F2a + F3 |
| A5 | Variable reference | F2b + F3 |
| A6 | Post-hoc correction | control |

**Mid-block test.** A3–A5 also run with block length 64 and a compact template that puts the equation and answer in the same block. This forces injection inside a block that is still denoising, which is the claim that separates this work from block-then-execute agents.

**Linux conditions:** no tools, conventional, async (F1 + F3 + F4). Each multi-call task also runs with F4 limited to one round, to measure what multi-turn adds.

**Controls kept from the last pilot:** the upstream sampler on dense native tool messages; artificial delay of 0, 10, 20 and 40 steps (now testing whether F3 fixes late arrivals).

## Metrics and gates

The gain is reported as two factors, so a miss shows which one failed.

```latex
\text{gain} \approx \underbrace{\frac{\text{insertions fired}}{\text{eligible prompts}}}_{\text{firing rate}} \times \underbrace{\frac{\text{wrong answers fixed}}{\text{insertions on wrong base answers}}}_{\text{use rate}} \times \text{base error rate}
```

**Metrics, per condition**

- Firing rate, with failed opportunities split by cause: absent, occupied, too short, late.
- Use rate and regression rate (right answers made wrong).
- Exact-match accuracy, direct and downstream.
- Mid-block share: insertions that land while their own block still has masked tokens.
- Re-mask count per result and per sequence (F3).
- Lock violations, stale completions, stray effects (all must be 0).
- Linux: answer present, strict format, calls per task, tasks completed only with multiple calls.

**Gates** (proposed; replace the original flat +30-point gate)

| Gate | Target |
| --- | --- |
| Firing rate, best of A3–A5 | ≥ 70% of eligible prompts |
| Use rate, same condition | ≥ 70% |
| Regression rate | ≤ 2% |
| Direct accuracy vs A0 | significant at p < 0.05, exact McNemar test, n = 240 |
| Mid-block share, block length 64 | ≥ 30% of insertions |
| Late-arrival use with F3, 40-step delay | ≥ 50% of delayed results used |
| Safety invariants | 0 lock violations, 0 stray effects |

Passing all gates on frozen weights would support the claim without fine-tuning. Failing only the mid-block gate would mean the method works but is a block-then-execute variant; that is useful, but not the novel claim.

## Run order, budget, risks

Build F3 first, because A3–A5 and the delay control all depend on it, then smoke-test each fix on the 36 original prompts before the 240-prompt run.

**Run order**

1. F3 re-mask on arrival, verified with the 40-step delay control.
2. F1 native `calc` tool: A2 and A3 on the 36 prompts.
3. F2a and F2b: A4 and A5 on the 36 prompts.
4. Full 240-prompt run of A0–A6 at block length 32.
5. Mid-block run: A3–A5 at block length 64 with the compact template.
6. F4 multi-turn runner, then the 27 Linux tasks.

**Budget** (estimate from the last pilot's \~125 s of sampling per 36 prompts): about 10 arithmetic condition runs over 276 prompts ≈ 3 GPU hours, plus Linux tasks and controls, so roughly 4–6 GPU hours on the retained A100, about $7–11 at $1.79/hour. Engineering time dominates.

**Risks and mitigations**

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Model doesn't call `calc` for sums it thinks it can do | low firing in A2–A3 | system prompt requiring `calc` for any operand over 4 digits; log refusals as a firing cause |
| Template changes, not fixes, cause the gain | false positive | A0 and A6 use the same template as each condition, minus the tool or slot |
| Frozen model won't write `<ref r1>` | A5 never fires | 2–3 few-shot examples in the prompt; report adoption rate |
| Re-masking makes answers worse | regressions | budget of 1 per result, 2 per sequence; regression rate is a gate |
| Re-masking oscillates on fast results | wasted steps | re-mask only text committed after the call was submitted |

**Decisions** (best guesses, chosen to keep the run simple and interpretable)

- **Dependent span: positional.** Re-mask the unlocked tokens from the result's position to the end of the current block, plus any later block already started. It is deterministic and easy to audit. As a diagnostic only, log each re-masked token's attention to the result, to inform a smarter rule in v1.2.
- **Native editing: yes, as A7, smoke set only.** After a result lands, allow LLaDA2.2's `DELETE`/`INSERT` edits on unlocked tokens of the dependent span instead of re-masking. Locks stay protected. Run it on the 36 prompts after F3 works; promote it to the full run only if it matches F3's use rate with fewer regressions.
- **Variable references for Linux: deferred to v2.1.** Keep v1.1 focused on arithmetic plus the existing Linux tasks.

**Defaults**

| Setting | Value | Why |
| --- | --- | --- |
| Reserved slot width (F2a) | result digits + 2 tokens, computed per prompt from operand lengths (sum of digits for ×, longest + 1 for + and −) | the result always fits; avoids too-short failures |
| Few-shot examples (F2b, F1) | 3 per prompt, same for every condition | enough to teach syntax; matched across conditions |
| `calc` requirement (F1) | system prompt: use `calc` for any operand over 4 digits | stops the model skipping the tool on hard sums |
| Trigger confidence τ | 0.9 on every operand token | matches the confidence gate DLLM Agent used |
| Re-mask budget (F3) | 1 per result, 2 per sequence | bounds cost and oscillation |
| Result budget (F4) | 256 tokens, then `[truncated]` | fits most synthetic files; follow-up reads cover the rest |
| Max tool rounds (F4) | 4 | covers the multi-call tasks without runaway loops |
| Decoding | temperature 0, fixed seed, block length 32 (64 for the mid-block run) | reproducible; same as the last pilot |

**Go/no-go checks on the 36 smoke prompts** (run before the 240-prompt run; fix or drop a condition that fails)

- [ ] F3: under the 40-step delay, at least one delayed result is used in the answer, with 0 lock violations.
- [ ] F1: the model calls `calc` on ≥ 50% of eligible prompts; otherwise strengthen the system prompt once, then report as is.
- [ ] F2a: no reserved slot is ever occupied by model text.
- [ ] F2b: `<ref r1>` adoption ≥ 50%; otherwise drop A5 from the full run and note it.
- [ ] All conditions: 0 lock violations, 0 stray effects, outputs reproduce exactly on a rerun of 5 prompts.
